# Swirl plan

Swirl is the Rust rewrite of Chocolate (game client and server) and vanilla (software avatar renderer). This file is the working plan: mapping, order, parity method and live status. Update it with every milestone.

## Phases

1. vanilla to parity: done for avatars, headshots, animations, R15, items, model, mesh and place scenes (with era and terrain parts). Draco meshes, WebP/GIF/BMP textures, scene Hint/Message overlays and a `--smooth=0` option are done; jpg/webp output is done in Solar's endpoint with GD; the 2016 renderer is dropped (Solar never selects it).
2. Switch Solar renders to Swirl: done. Solar calls only `bin/swirl`; the PHP renderer and the toggle file are gone; see Solar switch below.
3. 3D views. Finding: the site's 3D views (`avatar3d.js`, `chocolate/client/avatarview.js`) never call vanilla or Arbiter; they build the character in the browser from `/asset` data with chocolate's own renderer, so they keep working unchanged while renders move to Swirl. The Swirl-driven viewer is part of phase 5 (swirl-client compiled to wasm). Original idea, kept for phase 5: `swirl-vanilla` gets a `scene` mode that prints the data the viewer needs (per-part CFrames from `items::build_look`, converted meshes as typed arrays, textures as PNG URLs, body colours, stance), served next to the render endpoint. `js/mobile/avatar3d.js` asks for it and falls back to the current chocolate `avatarview.js` path on any error. Later, `swirl-render` compiled to wasm replaces the JS viewer. Not started.
4. swirl-core and swirl-server: instance tree, class tables, rbxl/rbxm readers, Lua host (mlua, lua51 + vendored), physics, humanoid, replication, WebSocket protocol identical to `chocolate/server`.
5. swirl-client (wasm32-unknown-unknown + wasm-bindgen, WebGL2 via wgpu or raw web-sys), 2012 and 2018 eras. The JS client keeps working against the Swirl server during the transition.

## Parity method

`tools/parity/run.sh <name> <options>` renders with the frozen PHP reference in `tools/parity/php-ref` (`tools/parity/php_render.php`: read-only fetcher over `/var/www/assets/assets` then `/cache`, throwaway cache dir under /tmp, never touches the live cache or slot locks) and with `swirl-vanilla`, then prints a pixel diff. `PARITY_EXACT=1` also renders PHP with `exact` (the reference rasteriser) and diffs against that, which isolates port errors from the fast-rasteriser approximation. Outputs are in `/tmp/swirl/<name>.{php,phpexact,swirl,diff,diffexact}.png`.

## Solar switch

Done. `core/class/Swirl.php` in Solar runs `/var/www/swirl/bin/swirl` with an argument list (no shell, 45 second limit), `--data=/var/www/assets/render-data` and `--assets=SOLAR_ASSETS`. `Arbiter` (avatar, headshot, animation, R15 package, item, model, mesh and place renders) calls only Swirl; on a failure it keeps the old image and logs to render.log. Assets that are on neither `assets/` nor `cache/` are printed as `missing: <id>` on stderr; `Solar\Swirl::render` fetches them from `/asset` into a temporary directory passed as `--extra-assets` and runs again, at most twice. `/api/v1/render` is `router/api/render/v1.php` (2012 renderer only; png, jpg and webp through GD). `MeshConverter` uses `mesh-convert` and `mesh-json`, and the body-colour and character-colour helpers use `body-colors` and `character-colors`. Render cache busting is `SOLAR_RENDER_VERSION` in `core/render.php`. The binary rejects unknown options (exit 2) so a stale binary can never answer a newer request wrongly.

Speed: 0.2 s per body render, 0.3 to 8 s per place against PHP's several seconds.

Verified headless: the wasm module parses Chocolate's own `init` snapshots and a Swirl server join in node (7 parts for place 564). The WebGL drawing path has not been run in a browser.

## Lua host and rep flushing (server slice 2)

- `swirl-lua::Host` loads Chocolate's `runtime.lua` unchanged (copy in `crates/swirl-lua/data/`, plus `luadata.lua` generated by `tools/dump-luadata.mjs`) into Lua 5.1 through mlua (`unsafe_new`, because the runtime needs the debug library and removes it itself). It implements the host table the runtime expects: `get`, `set`, `call`, `new`, `sub`, `unsub`, `poll`, `alive`, `running`, `log`, `now`, `side`, `data`, with the tagged flat wire format.
  Supported so far: properties by class table (bool, string, number, enum, V3, C3, CF, Ref, BC), Parent, Name, ClassName, children and services by name, methods GetChildren, GetDescendants, FindFirstChild (recursive flag), FindFirstChildOfClass, FindFirstChildWhichIsA, GetFullName, IsA, IsDescendantOf, IsAncestorOf, Clone, Destroy, ClearAllChildren, GetService, Instance.new, and the events ChildAdded, ChildRemoved, DescendantAdded, Changed (property sets from Lua), PlayerAdded.
  Not yet: UDim2/Vector2/Ray/enum wire types in set, Touched and every physics or humanoid event, Humanoid and Player methods, RunService events, BindableEvent and RemoteEvent, LoadAsset and the other async methods, CoreScripts, `rep` of changes made by code other than the Lua host.
- `swirl-core::DataModel` keeps a change journal; `swirl-server` flushes it every 33 ms as Chocolate `rep` operations (`p`, `n` with whole subtrees, `m`, `d`), only for replicated, non-player-scoped instances.
- Check: `tools/swirl-rep-test.mjs <port>` with a test place at `/tmp/swirl/fakeassets/assets/9001` (a Script that creates, renames and destroys parts): the unmodified Chocolate codec and DataModel in node end up with the expected Workspace.

## Swirl server joined from a browser (client 1.12)

`swirl-server --place=ID --port=N` now spawns an R6 character per player (Humanoid, Torso, Head with a Head SpecialMesh, arms, legs, body colours, at the first SpawnLocation), sends `after.own` to the owner, accepts `char` messages and relays them to the other players as `ch` records. ## Server 3: Touched, health, events, tickets

## Client Lua and GUI (1.15)

Route chosen: run Chocolate's own client engine in the browser next to the wasm world, instead of porting the Lua host to the wasm build. `crates/swirl-client/lua.js` (loaded by `entry.js` as `./lua.js`) injects an import map for `three`, `wasmoon-lua5.1`, `@dimforge/rapier3d-compat` and `lodash` pointing at `<publicPath>/client/vendor/`, then imports Chocolate's unchanged `client/world.js`, `client/gui.js`, `client/input2018.js`, `shared/luahost.js`, `shared/core2018.js` and `client/assets.js` from the Chocolate public path (`/chocolate`). `SwirlWorld` subclasses `ClientWorld` and replaces what Swirl's Rust client owns: characters, the controller, physics and rendering (`trackChar`, `dropChar`, `charDied`, `takeOwnership` are stubs, `physics` is a stub whose `raycast` is a ray against the replicated part boxes). It keeps everything else: the JS DataModel fed by the same `init` and `rep` messages (the wasm client taps every raw message with `Client.take_tap()`), the wasmoon Lua host with `runtime.lua` and `runtime2018.lua`, CoreScript loading (2012: StarterScript and its AddCoreScript tree from `/asset`; 2018: `corescripts2018/bundle.json`), RemoteEvent and RemoteFunction (`onRemote`, `env.remote`, over the existing `re`, `rfc`, `rfr` messages), Mouse (Hit, Target, Button1Down/Up, Move, Icon through `updateMouse` and the `mouse` and `act` messages), tools (equip and unequip through the Lua backpack and `toolMoved`), UserInputService and ContextActionService (`Input2018`), RunService (Stepped, Heartbeat, RenderStepped), the Camera (CFrame, ViewportSize copied each frame from the Rust camera through `Client.camera_pose()`) and the whole DOM GUI layer (`Gui`: ScreenGui, Frame, TextLabel, TextButton, TextBox, ImageLabel, ImageButton, ScrollingFrame, UI layouts, 2012 and 2018 properties, mouse and text input) drawn as an overlay above the WebGL canvas, exactly as Chocolate draws it.
Why: Chocolate's host is 1.7k lines of `luahost.js` plus 650 of `api2018.js` and the 2018 CoreScripts need most of it; porting that to Rust for the wasm client would take weeks and diverge from CoreScripts that are "run exactly as given". The JS engine runs them unchanged on the first try, the client build stays 3 s incremental (no Lua in the wasm), and parity with Chocolate is automatic. Cost: a second, JS-side copy of the instance tree in the browser (the Rust world still draws), about 2 MB of Chocolate modules and three.js loaded at join, and the dependency on Chocolate's public files being served (`/chocolate/client`, `/chocolate/shared`, `/chocolate/corescripts2018`, `/chocolate/content*`). Lua writes to the world (a LocalScript moving a part, Lua-driven camera or movement in 2018) do not reach the Rust renderer yet; the Rust client keeps WASD, the follow camera and its own character animation, and the 2018 PlayerModule's Lua movement and camera output is ignored.

### Step 1: Lua 5.1 inside the Rust wasm build (done in 1.19)

Route chosen: mlua (lua51, vendored) compiled to `wasm32-unknown-unknown`, the same crate and Lua 5.1.5 the server uses, so `swirl-lua`'s `Host` and Swirl's own `runtime.lua` and `runtime2018.lua` run unchanged in the browser. Rejected: a pure Rust Lua (no faithful 5.1 with the Roblox runtime's metatable, coroutine and pcall behaviour; piccolo and similar target 5.3/5.4 semantics); keeping wasmoon (a JS dependency and a second Lua build the owner wants gone); a separate Lua wasm module (the host would cross a JS boundary on every Lua call).

How it builds:
- `.toolchain/` (git-ignored, `tools/setup-toolchain.sh` downloads wasi-sdk 34, run automatically by `build-client.sh`) provides clang and the wasi-libc archives. `tools/wasm-cc.sh` is `CC_wasm32_unknown_unknown` (set in `.cargo/config.toml` `[env]`): it compiles C for `wasm32-wasip1` with `-mexception-handling -mllvm -wasm-enable-sjlj -mllvm -wasm-use-legacy-eh=true`, so Lua's `setjmp`/`longjmp` error handling becomes wasm exceptions, and defines `L_tmpnam`.
- `vendor-crates/lua-src` is `lua-src` 547.0.0 with only Lua 5.1.5 and a `wasm32-unknown-unknown` branch (`LUA_USE_LONGJMP`); `[patch.crates-io]` in the workspace `Cargo.toml` uses it for every target.
- The wasm link adds `libsetjmp.a` and `libc.a` from the sysroot (rustflags in `.cargo/config.toml`). `tmpfile`, `clock`, `system` and `tmpnam` are stubbed in `luavm.rs` because `liolib` and `loslib` reference them. The libc imports (`wasi_snapshot_preview1`, 17 functions: environ, clock, fd_*, path_*, proc_exit) are satisfied by `swirlWasi()`, which `tools/patch-wasi.mjs` inserts into the generated `swirl_client.js` (wasm-bindgen emits `import ... from "wasi_snapshot_preview1"` otherwise, which a browser cannot resolve).
- wasm-bindgen 0.2.100 cannot parse exception-handling wasm, so the crate and the installed CLI moved to 0.2.121 (`cargo install wasm-bindgen-cli --version 0.2.121`; the 0.2.100 binary is not kept in the repo).
- `swirl-lua` no longer calls `Instant` or `SystemTime` (they panic on wasm): `clock.rs` keeps the native behaviour and, on wasm, reads a clock the client sets (`set_now`, `set_wall`).

Result: `crates/swirl-client/src/luavm.rs` exposes `LuaVm` (a client `DataModel` plus `swirl_lua::Host`); `tools/luavm-test.mjs <dist>` runs a script in node (print, pcall with error, Instance.new, spawn/wait) and boots in about 50 ms. Build times: clean wasm client 53 s (was 27 s), incremental 1 s, `build-client.sh` end to end 5 s; wasm 1.63 MB (was 0.85 MB) before the host is wired in. Clean build profile (`cargo --timings`): web-sys 17.6 s and js-sys 16 s (wasm-bindgen 0.2.121 pulled web-sys 0.3.98, slower than 0.3.77), swirl-core 8.9 s, the Lua C sources in mlua-sys 7.2 s, mlua 6.9 s; so caching the compiled Lua objects would save at most 7 s and is not worth a custom cache, and Lua is not the main clean-build cost. Incremental builds are unaffected. Movement parity unchanged (18 scenarios, 3769 frames, 0 difference).

Next in step 1: a client `DataModel` fed by `init` and `rep` (swirl-core), the Lua client host mirroring `luahost.js` (CoreScript loading, Mouse, UserInputService, RunService, RemoteEvents, GUI object API), then dropping wasmoon and `lua.js`'s DataModel.

## Server port: independence, config and feature inventory (server 4)

Owner direction: Swirl is 1:1 with Chocolate and vanilla but in Rust and depends on neither. Done for the server:

- `config.local.php` (gitignored, array of `redeem_url`, `redeem_key`, `site_url`; optional `port`, `assets_dir`, `data_dir`, `presence_path`, `log_file`, committed template `config.example.php`) is read by `swirl-server` (`config.rs`, a small parser for that array format). - DataStore and per-player data are stored in `data/store/` (gitignored; `data_dir` or `SWIRL_STORE`), in Chocolate's formats (`<place>.json` store map; `players/<place>/<uid>.json` with n, s, b, i).

### Hosting Solar games on Swirl (Solar side, developer-only, off by default)

Solar reads optional `CONFIG` keys: `swirl_server_port` (for example 4210) and `swirl_server_ws` (the WebSocket path or URL the client connects to, for example `/swirl/ws` through an Apache `ProxyPass`), plus optional `swirl_server_host` (default 127.0.0.1) and `swirl_server_key` (default: the same HMAC key Chocolate uses). With either of the first two empty, the feature is off and nothing changes. When on, developers (Role >= 3) get a Game server select on a game's Configure page (Game Settings); `ChocolatePlaceSettings.GameServer` (`chocolate` or `swirl`, added on first use) decides which server `ticket.php` points the client at, and the admin Servers tab, the game page's server list and `chocolate_status()` show both servers (Swirl entries are tagged). Nothing is switched to Swirl by default.
